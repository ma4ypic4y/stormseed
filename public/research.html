Can the sky
make a random number?

Yes. But “unpredictable weather” and “a secure random generator” are different claims. Here is what this project can honestly do.

Research and implementation notes · October 22, 2026

The idea has a real history.

RANDOM.ORG describes lightning-induced atmospheric radio noise as the source for its random data. Its radio receivers sample physical noise. That is close to the original intuition, but it is not the same as hashing a published catalogue of lightning locations.

In RFDIDS (NDSS 2019), Georgia Tech researchers used lightning radio signals as a naturally occurring, quasi-random pattern to check the integrity of power-grid receiver data. It is evidence of a related physical mechanism, not a certification of this generator.

These sources establish relevant prior art. They do not prove that nobody has built an identical satellite-based picker, and this project makes no “world’s first” claim.

What the satellite actually sees.

The Geostationary Lightning Mapper observes optical lightning flashes, including in-cloud and cloud-to-cloud activity. A flash record is not necessarily a ground strike. GOES-19 and GOES-18 have regional fields of view over the Western Hemisphere. The project does not observe the whole planet.

We collect up to two recent 20-second GLM Level 2 files per satellite, retain records with a good flash-quality flag and finite measurements, and include timestamps, centroids and radiant energy. The two views may overlap. We call the count “flash observations,” not a count of independent worldwide strikes. If one satellite is unavailable, a snapshot can use the other; its actual source list is preserved.

How much randomness does lightning add?

We cannot responsibly assign a number of entropy bits to this feed. Lightning is difficult to predict, but nearby events share a storm. Measurements are quantized; processing, filtering and geography add structure. A timestamp’s last digit is not automatically an unbiased random bit.

After publication, an observer who knows the entire snapshot has no remaining uncertainty about that snapshot. Hashing it cannot make it secret again. A 256-bit hash is a 256-bit output, not proof of 256 bits of physical entropy. Passing a histogram or a statistical test would not establish unpredictability.

NIST SP 800-90B treats entropy-source assessment, conditioning and health tests as explicit engineering tasks. We have not validated this satellite pipeline under that standard. A future lightning-only mode would need a documented adversary model, raw-source assessment, conservative min-entropy estimates and continuous health tests.

The method we actually ship.

Each request gets 32 new bytes from crypto.getRandomValues. We combine that nonce with a SHA-256 fingerprint of the real lightning snapshot, the range and a counter. This is a hybrid construction. The fresh unpredictability rests on the browser’s random generator and the cryptographic hash, without assuming secret entropy in public data. The browser API is specified in the W3C Web Cryptography API.

seed = SHA-256(snapshot material)
block = SHA-256(JSON(["stormseed-v1", seed, nonce, min, max, counter]))
result = min + rejection_sample(block, max − min + 1)

We read the block as eight unsigned 32-bit words, in order. For a range of size n, we accept only words below floor(2³²/n) × n. Every residue then has the same number of accepted inputs. If all eight words are rejected, the counter increases and a new block is hashed. This removes modulo bias under the usual uniform-word model; it does not independently certify the source.

The interface offers numbers from 1 to 100 and a six-sided die. Both use the same inclusive integer mapping. No result comes from JavaScript’s Math.random.

A receipt, not a certificate.

A downloadable receipt contains the exact serialized snapshot, its fingerprint, original file URLs and SHA-256 hashes, the browser nonce, settings and result. The open-source verifier reproduces the result and checks the snapshot fingerprint. Fetching the original source files and checking their hashes is a separate provenance check.

A receipt cannot prove that a user did not reroll, select a favourable nonce, alter the website or present a fabricated draw. The displayed flash is one member of the input snapshot; it is not a claim that one particular bolt uniquely caused the outcome. The brief red discharge is a visual response, not a recorded lightning path.

Use Stormseed for small decisions, casual games and creative prompts. For passwords, use a password manager. Audited giveaways need a separate commitment, timestamp and verification design; valuable draws should use a suitable established service.

Why someone would return — and share.

The recurring job is small: pick a page, break a tie, play a game, roll a die. Two fixed modes — 1–100 and a six-sided die — keep that job one action away. There is no sign-in and no analytics or advertising code in the project. Results stay in the browser unless the visitor chooses to export or share them; the hosting provider still handles ordinary web requests.

The shareable object is a quiet, well-made result card: the answer in expressive typography, the observation time and a link back. Sharing is useful because it communicates the decision, not because it interrupts the visitor. The result itself becomes the main graphic, so an ordinary choice leaves a simple, shareable object.

The launch proposition is simple: “I built a random picker seeded by actual lightning.” Show one short screen recording: generate a number, roll the die, reveal the source, save the card. Credit NOAA, show the limitation plainly, and link directly to the tool. This is a product hypothesis, not evidence that it will go viral.

Evaluate it by whether people complete a choice, use it again, and share the result. Without tracking, initial evidence can come from voluntary feedback and public reactions. Do not add invasive analytics merely to manufacture a growth dashboard.

Keeping it honest over time.

A GitHub Actions workflow refreshes observations around twice an hour and deploys the static site to GitHub Pages. Scheduled jobs can be delayed or fail. The last successfully deployed snapshot remains available and its actual age stays visible; after two hours it is labelled older data. No fake live counter or fabricated lightning fallback is used.

GitHub can disable scheduled workflows in public repositories after prolonged inactivity. The repository documents re-enabling the schedule. A public-data service also has no uptime guarantee, so the interface treats freshness as observable information rather than a promise.

The most useful next experiment is a shared “let the next storm decide” session with a commitment to choices before future data arrives. That requires an independently timestamped record and a backend; it is deliberately outside this static first version.
